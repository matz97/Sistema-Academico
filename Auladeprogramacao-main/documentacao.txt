DOCUMENTACAO COMPLETA DO SISTEMA ACADEMICO

Atualizado em: 23/05/2026


1. VISAO GERAL

O Sistema Academico e uma aplicacao desenvolvida em Python para gerenciar
informacoes academicas de uma instituicao de ensino.

O projeto possui duas partes principais:

- Um prototipo orientado a objetos, executado pelo terminal, com classes como
  Pessoa, Aluno, Professor, Disciplina e SistemaAcademico.
- Uma aplicacao web em Flask, com persistencia em banco de dados, login,
  controle de perfis, telas de cadastro, boletim e relatorios.

A versao web e a principal interface de uso do sistema.


2. OBJETIVOS DO SISTEMA

O sistema tem como objetivos:

- Cadastrar e listar alunos.
- Cadastrar e listar professores.
- Cadastrar e listar disciplinas.
- Vincular professores a disciplinas.
- Matricular alunos em disciplinas.
- Registrar notas e carga horaria no boletim.
- Consultar boletim por perfil de usuario.
- Gerenciar usuarios do sistema.
- Controlar permissoes por perfil.
- Gerar relatorios em JSON e PDF.
- Usar MySQL em ambiente completo ou SQLite local para testes.

5. ARQUITETURA GERAL

A aplicacao segue uma estrutura simples:

1. O usuario acessa a aplicacao pelo navegador.
2. O Flask recebe a requisicao em app.py.
3. A rota verifica login e perfil do usuario.
4. A rota consulta ou altera dados usando funcoes de db.py.
5. O Flask renderiza um template HTML da pasta templates/.
6. O navegador exibe a pagina com estilos de static/styles.css.

As principais camadas sao:

- Interface: templates HTML, CSS e JavaScript.
- Aplicacao: rotas e regras em app.py.
- Persistencia: funcoes e conexoes em db.py.
- Relatorios: geracao de JSON/PDF em relatorios.py.
- Banco: MySQL ou SQLite.


6. BANCO DE DADOS

O sistema pode usar dois bancos:

- MySQL: banco principal recomendado.
- SQLite: banco local automatico para desenvolvimento e testes.

6.1 MySQL

O arquivo schema.sql cria:

- Banco sistema_academico.
- Tabelas alunos, professores, disciplinas, matriculas e usuarios.
- Relacionamentos entre disciplinas/professores e matriculas/alunos.
- Dados iniciais para teste.

6.2 SQLite

Se o MySQL nao estiver disponivel e MYSQL_REQUIRED nao estiver ativado, o
sistema cria e usa um banco SQLite local.

O caminho padrao e:

sistema_academico.sqlite3

Esse caminho pode ser alterado pela variavel SQLITE_PATH.

6.3 Selecao automatica do banco

O arquivo db.py tenta conectar no MySQL. Se conseguir, usa MySQL. Se falhar e
MYSQL_REQUIRED nao estiver ativo, usa SQLite.

Se MYSQL_REQUIRED for 1, true ou yes, a aplicacao exige MySQL e exibe erro se
nao conseguir conectar.


7. TABELAS DO BANCO

7.1 alunos

Armazena os alunos do sistema.

Campos:

- id
- nome
- cpf
- matricula
- curso
- criado_em

Regras:

- cpf deve ser unico.
- matricula deve ser unica.

7.2 professores

Armazena os professores.

Campos:

- id
- nome
- cpf
- registro
- area
- criado_em

Regras:

- cpf deve ser unico.
- registro deve ser unico.

7.3 disciplinas

Armazena as disciplinas.

Campos:

- id
- nome
- codigo
- carga_horaria
- professor_id
- criado_em

Regras:

- codigo deve ser unico.
- professor_id referencia professores.id.
- Se o professor for removido do banco, a disciplina fica sem professor.

7.4 matriculas

Armazena o vinculo entre aluno e disciplina.

Campos:

- id
- aluno_id
- disciplina_id
- nota1
- nota2
- ativo
- removido_em
- criado_em

Regras:

- aluno_id referencia alunos.id.
- disciplina_id referencia disciplinas.id.
- O par aluno_id + disciplina_id deve ser unico.
- ativo indica se a matricula aparece na interface.
- removido_em registra quando a matricula foi removida logicamente.

7.5 usuarios

Armazena os usuarios que podem acessar o sistema.

Campos:

- id
- usuario
- senha_hash
- perfil
- aluno_id
- professor_id
- criado_em

Regras:

- usuario deve ser unico.
- senha_hash armazena a senha criptografada.
- perfil pode ser admin, professor ou aluno.
- aluno_id e usado quando o perfil e aluno.
- professor_id e usado quando o perfil e professor.
- Somente admin pode criar, editar e excluir usuarios.

Restricoes:

- Nao pode gerenciar usuarios.
- Nao pode gerar relatorios administrativos.


9. LOGIN E SESSAO

9.1 Login

Rota:

/login

O usuario informa:

- Usuario
- Senha

O sistema consulta a tabela usuarios e valida a senha usando hash.

Tambem existe um login administrativo de desenvolvimento:

- Usuario padrao: teste123
- Senha padrao: 12345
- Perfil: admin

Esses valores podem ser alterados por:

- LOGIN_USER
- LOGIN_PASSWORD

9.2 Sessao

Apos o login, o sistema grava na sessao:

- usuario_logado
- perfil
- aluno_id
- professor_id

Esses dados sao usados para controlar menus, acessos e consultas.

9.3 Logout

Rota:

/logout

Metodo:

POST

Ao sair, a sessao e limpa.


10. GERENCIAMENTO DE USUARIOS

Rota principal:

/usuarios

Somente admin acessa essa area.

Funcionalidades:

- Listar usuarios cadastrados.
- Criar usuario.
- Escolher perfil.
- Vincular usuario a aluno.
- Vincular usuario a professor.
- Editar usuario existente.
- Alterar senha.
- Excluir usuario.

Regras:

- Usuario deve ter pelo menos 3 caracteres.
- Senha deve ter pelo menos 4 caracteres.
- Confirmacao de senha deve conferir.
- Perfil aluno exige aluno vinculado.
- Perfil professor exige professor vinculado.
- Perfil admin nao exige vinculo.
- Um admin nao pode excluir o proprio usuario logado.

Rotas:

- GET /usuarios
  Lista usuarios e exibe formulario de cadastro.

- POST /usuarios
  Cria um novo usuario.

- GET /usuarios/<id>/editar
  Exibe formulario de edicao.

- POST /usuarios/<id>/editar
  Atualiza usuario, perfil, vinculo e opcionalmente senha.

- POST /usuarios/<id>/excluir
  Exclui o usuario.

16. BOLETIM

Rota:

/boletim

Perfis permitidos:

- admin
- professor
- aluno

Comportamento por perfil:

- Admin pode selecionar qualquer aluno.
- Professor pode selecionar alunos matriculados em suas disciplinas.
- Aluno visualiza automaticamente somente o proprio boletim.

Dados exibidos:

- Nome do aluno.
- Matricula.
- CPF.
- Curso.
- Codigo da disciplina.
- Nome da disciplina.
- Professor.
- Carga horaria.
- Nota 1.
- Nota 2.
- Media.
- Status.

Calculo da media:

media = (nota1 + nota2) / 2

Status:

- Aprovado: media maior ou igual a 7.
- Recuperacao: media menor que 7.
- Aguardando notas: quando alguma nota ainda nao foi preenchida.


17. EDICAO DE BOLETIM

Validacoes:

- Nota deve estar entre 0 e 10.
- Campo vazio em nota salva valor nulo.
- Carga horaria deve ser maior que zero.

Aluno nao pode editar boletim.

21. FUNCOES IMPORTANTES EM app.py

- parse_nota(valor)
  Converte e valida nota entre 0 e 10.

- parse_carga_horaria(valor)
  Converte e valida carga horaria maior que zero.

- perfil_atual()
  Retorna o perfil salvo na sessao.

- usuario_admin()
  Informa se o usuario atual e admin.

- usuario_professor()
  Informa se o usuario atual e professor.

- usuario_aluno()
  Informa se o usuario atual e aluno.

- exigir_perfil(*perfis)
  Verifica se o usuario possui um dos perfis permitidos.

- professor_pode_editar_matricula(matricula_id)
  Verifica se o professor logado pode editar determinada matricula.

- exigir_login()
  Bloqueia rotas privadas quando nao ha usuario logado.

- get_dashboard_counts()
  Calcula os totais do painel.

- get_dados_relatorio_banco()
  Monta os dados usados pelos relatorios.


22. FUNCOES IMPORTANTES EM db.py

- _connect_mysql()
  Abre conexao com MySQL.

- _connect_sqlite()
  Abre conexao SQLite e garante o schema local.

- _ensure_engine()
  Decide qual banco sera usado.

- is_sqlite()
  Retorna se o banco atual e SQLite.

- database_label()
  Retorna uma descricao do banco atual.

- _ensure_sqlite_schema(connection)
  Cria e ajusta tabelas no SQLite.

- _ensure_mysql_schema(connection)
  Garante colunas de usuarios no MySQL.

- get_connection()
  Abre conexao e controla commit/rollback.

- _prepare_query(query)
  Adapta placeholders %s para ? quando o banco e SQLite.

- fetch_all(query, params=None)
  Executa SELECT retornando varias linhas.

- fetch_one(query, params=None)
  Executa SELECT retornando uma linha.

- execute(query, params=None)
  Executa comandos INSERT, UPDATE e DELETE.

26. VARIAVEIS DE AMBIENTE

- FLASK_SECRET_KEY
  Chave usada pelo Flask para assinar sessoes.

- FLASK_DEBUG
  Ativa o modo debug somente quando configurado como 1, true ou yes.
  Em uso fora do desenvolvimento, deve permanecer desativado.

- LOGIN_USER
  Usuario admin inicial de desenvolvimento.

- LOGIN_PASSWORD
  Senha do admin inicial de desenvolvimento.

- MYSQL_HOST
  Host do MySQL.

- MYSQL_PORT
  Porta do MySQL. Padrao: 3306.

- MYSQL_USER
  Usuario do MySQL.

- MYSQL_PASSWORD
  Senha do MySQL.

- MYSQL_DATABASE
  Nome do banco. Padrao: sistema_academico.

- MYSQL_REQUIRED
  Se 1, true ou yes, obriga uso do MySQL.

- SQLITE_PATH
  Caminho do arquivo SQLite local.

28. VALIDACOES E MENSAGENS

O sistema exibe mensagens para:

- Login realizado com sucesso.
- Usuario ou senha invalidos.
- Usuario cadastrado com sucesso.
- Usuario atualizado com sucesso.
- Usuario excluido com sucesso.
- Falta de permissao.
- Aluno nao encontrado.
- Professor nao encontrado.
- Disciplina nao encontrada.
- Matricula nao encontrada.
- CPF, matricula, registro ou codigo duplicado.
- Aluno ja matriculado na disciplina.
- Notas fora do intervalo permitido.
- Carga horaria invalida.


29. LIMITACOES ATUAIS

- Nao ha testes automatizados formais.
- Nao ha migrations versionadas com ferramenta propria.
- O login admin padrao e adequado apenas para desenvolvimento.
- A exclusao de usuarios e fisica, nao logica.
- Alunos, professores e disciplinas nao possuem exclusao pela interface.
- A tela de cadastro antiga ainda existe como arquivo, mas nao e usada no fluxo.
- O PDF e gerado de forma simples, sem biblioteca externa de layout.

- Admin conseguindo gerenciar alunos, professores, disciplinas, matriculas e
  usuarios.
- Professor visualizando e editando somente boletins das suas disciplinas.
- Aluno visualizando somente o proprio boletim.
- Campos obrigatorios bloqueando envio vazio ou somente com espacos.
- Cadastros duplicados bloqueados pelo banco e pela aplicacao.
- Pesquisa funcionando por texto parcial e sem diferenciar maiusculas de
  minusculas.
- Matricula duplicada bloqueada.
- Remocao de matricula preservando historico no banco.
- Relatorios JSON e PDF gerados corretamente.
- README e documentacao suficientes para instalacao e execucao.
- Modo debug desativado por padrao.


31. PLANO DE HOSPEDAGEM NA AWS

Uma forma recomendada de publicar o sistema e usar:

- GitHub como repositorio.
- AWS Elastic Beanstalk para hospedar Flask.
- Amazon RDS for MySQL para o banco.
- AWS CodePipeline para deploy automatico.

Etapas:

1. Versionar o codigo no GitHub.
2. Criar banco RDS MySQL.
3. Executar schema.sql no RDS.
4. Criar ambiente Python no Elastic Beanstalk.
5. Configurar variaveis de ambiente no Elastic Beanstalk.
6. Criar pipeline conectando GitHub ao Elastic Beanstalk.
7. Adicionar etapa de build/teste com CodeBuild.
8. Validar login, cadastros, boletins e relatorios em producao.

Variaveis importantes em producao:

- MYSQL_HOST
- MYSQL_PORT
- MYSQL_USER
- MYSQL_PASSWORD
- MYSQL_DATABASE
- MYSQL_REQUIRED=1
- FLASK_SECRET_KEY
- LOGIN_USER
- LOGIN_PASSWORD
